# 任意阅读体验词稳定兑现设计

状态：已确认

日期：2026-07-17

范围：开书、第一章、续章、重写、状态抽取、修史与发布验收

## 1. 背景

当前系统已经能把两个“阅读时的感觉”保存为 `ReadingExperienceContract`，但还没有真正做到通用兑现：

- 已策展词依赖固定定义，未知词统一退化为“主角行动”，导致文风、节奏、关系和世界反应类词语被错误解释。
- “系统”“无敌”的提示、验证、事实持久化和本地兜底散落在多个调用点，并通过词面分支启用。
- 单句原文证据适合验证机制、行动和冲突结果，却无法证明“冷冽”“轻盈”“慢热”等全章分布性质。
- 第一章、续章、重写、抽取与修史没有共享同一份可执行规则，因此提示要求与发布门禁会漂移。
- 固定开头骨架能让窄测试通过，却造成重复、僵硬和题材不适配，不能代表真实质量。

本设计把两个词先编译为一份版本化、可调度、可验收的阅读体验契约，再让所有叙事阶段消费同一份契约。

## 2. 目标与产品承诺

### 2.1 目标

1. 每个被系统接受的词对都生成两个独立、同等重要的体验维度。
2. 规划、正文、重写、抽取、续章和修史使用同源规则，不再由调用方按词面判断。
3. 机制、行动、关系、冲突、世界反应、节奏和文风分别使用适合自己的证据方式。
4. 两个维度在同一故事因果中兼容，不能静默牺牲其中一个。
5. 每个在 V2 契约生效后新发布或重新修订的章节都能证明两个维度已经兑现；证明不足时重写或阻断，而不是发布差稿。
6. 跨章兑现通过体验账本持续追踪；修史后证据和账本随正史一起重放。
7. 无意义、无法可靠解释、不可调和或不安全的输入在正文模型调用前明确拒绝，且不消耗正文生成 Token。

### 2.2 “无论输入什么词”的精确定义

系统对任意格式合法输入都必须给出确定结果：

- 安全、可解释、可同时兑现的词对：接受，并在所有发布章节中稳定兑现。
- 有文学张力但表面冲突的词对，例如“治愈 · 残酷”：合成为同一因果张力，两个维度分别验收。
- 重复或近义词，例如“温暖 · 温暖”“轻快 · 轻盈”：拆成互补表现层，仍要求两份不同证据。
- 低置信、无意义或真正不可调和的词对：返回可理解的换词提示，不假装能够保证。
- 提示注入、危险或越权输入：在任何外部模型调用前拒绝。

“稳定兑现”不等于正文逐字出现两个词，也不等于任何能力不足的模型都能生成合格正文。它表示 V2 契约生效后，系统不会发布没有可靠兑现证据的新章节或新修订；重试仍不合格时，作业明确失败且不污染正史。

### 2.3 非目标

- 不承诺无意义字符串也能产生高质量文学解释。
- 不通过模仿在世作者来满足风格输入；此类输入只可转译为抽象、通用的文风维度。
- 不让规划模型生成可执行代码、正则或任意规则脚本。
- 不向普通读者展示后台契约、规则图、评分过程或提示词。
- 不把阅读体验账本当作人物知识或故事正史。

## 3. 方案选择

比较过三种架构：

1. 三入口体验内核：`compile`、`schedule`、`assess`。
2. 单入口状态机：所有阶段通过一个 `advance` 方法推进。
3. 一站式故事流水线：开书、续章、重写和修史都由同一高层模块完成。

采用方案 1。它在现有代码中形成清楚的 Seam，同时保留模型路由、流式输出、Token 预算与正史事务的既有所有权。方案 2 的不透明状态和阶段结果用于内部设计；方案 3 可在应用层形成便捷门面，但不承担阅读体验领域规则。

## 4. 核心模块与接口

建立深模块 `ReadingExperienceModule`。唯一原始词输入 Seam 位于故事创建之前；契约生成后，业务调用方只能传递契约、账本和阶段票据，不得读取词语来决定行为。

```ts
interface ReadingExperienceModule {
  compile(request: CompileExperienceRequest): Promise<ExperienceOperationResult<CompileOutcome>>;
  schedule(request: ScheduleExperienceRequest): ExperienceStagePlan;
  assess(request: AssessExperienceRequest): Promise<ExperienceOperationResult<ExperienceAssessment>>;
}

type ExperienceOperationResult<T> =
  | { ok: true; value: T }
  | { ok: false; error: ExperienceOperationError };
```

预期的意图或质量判断使用领域结果；模型不可用、协议错误、正史过期和提交失败使用稳定的 `ExperienceOperationError`。调用方只处理结果类别，不解析供应商响应或规则内部文本。

### 4.1 `compile`

把阅读体验意图编译为不可变的体验契约修订和初始体验账本。

结果只有三种：

- `ready`：契约完整、安全、两个维度可合成，可以进入规划。
- `needs_resolution`：词义低置信或两个维度不可可靠合成，前端提示更换或澄清词语。
- `rejected`：输入不安全、构成提示注入或不符合格式。

`compile` 是唯一允许理解原始词语的入口。其余代码不得出现 `sourceWords.includes(...)`、`word === ...` 或等价词面分支。

### 4.2 `schedule`

根据契约修订、体验账本、正史视图和当前阶段，生成同源的阶段计划：

- 规划：故事蓝图必须兑现的体验结果和禁止方向。
- 开篇：本章激活信号、出现窗口、证据与持久状态要求。
- 续章：本章必须交付的信号、可轮换信号、跨章沿用和体验债。
- 重写：由失败规则生成定向修复要求，不把原始内部错误直接塞给正文模型。
- 抽取：为当前正文和当前契约生成证据 Schema。
- 修史：确定受影响章节、失效证据和账本重放范围。

阶段计划带不可伪造的票据，固定契约修订、账本修订、正史版本、阶段和规则版本。规划提示、正文提示、抽取要求和发布门禁都从同一规则图投影，消除漂移。

### 4.3 `assess`

验证规划蓝图、正文、抽取声明或修史结果，并返回：

- `needs_extraction`：本地预检通过，需要外部模型抽取或语义裁判。
- `accepted`：硬承诺全部通过，返回已落地证据和账本补丁。
- `rewrite`：可修复的体验违约，返回稳定规则编号和定向重写令牌。
- `rejected`：安全、契约冲突或修史破坏正史等不可发布结果。

只有 `accepted` 能进入正史提交事务。

## 5. 领域数据模型

### 5.1 阅读体验意图

```ts
interface ReadingExperienceIntent {
  descriptors: readonly [
    { text: string; clarification?: string },
    { text: string; clarification?: string },
  ];
  locale: "zh-CN";
}
```

原词始终保存用于展示和审计，但永远不作为正文关键词要求。

### 5.2 体验契约修订 V2

```ts
interface ExperienceContractRevision {
  id: string;
  schemaVersion: 2;
  revision: number;
  parentRevisionId: string | null;
  status: "draft" | "active" | "superseded";
  effectiveFrom: { branchId: string; chapterNumber: number; canonVersion: number };
  dimensions: readonly [ExperienceDimension, ExperienceDimension];
  synthesis: ExperienceSynthesis;
  promises: DeliveryPromise[];
  prohibitions: ExperienceProhibition[];
  ruleGraphVersion: string;
  provenance: ExperienceProvenance[];
  createdAt: string;
}
```

契约修订不可变。用户未来换词会创建新修订并从指定章节起生效；追溯修改既有章节必须进入修史流程。

### 5.3 体验维度

```ts
type ExperienceCategory =
  | "mechanic"
  | "protagonist_action"
  | "conflict_outcome"
  | "world_reaction"
  | "relationship"
  | "pacing"
  | "voice";

interface ExperienceDimension {
  id: string;
  descriptor: string;
  interpretation: string;
  categories: readonly [ExperienceCategory, ...ExperienceCategory[]];
  observableSignals: ObservableSignal[];
  prohibitions: ExperienceProhibition[];
  confidence: number;
}
```

一个词可以属于多个类别，例如“史诗”可同时作用于世界反应和叙述尺度；不能再把未知词全部归入主角行动。

### 5.4 可观察信号

```ts
interface ObservableSignal {
  id: string;
  dimensionId: string;
  kind: ExperienceCategory;
  description: string;
  semanticSlots?: {
    actor?: string;
    action?: string;
    object?: string;
    outcome?: string;
    reaction?: string;
  };
  verification: EvidencePolicy;
  persistence: "none" | "chapter" | "cross_chapter" | "whole_story";
}
```

模型只能提出语义槽和值，进程内编译器把它们映射到白名单规则；模型不能创建可执行规则。

### 5.5 交付承诺

```ts
interface DeliveryPromise {
  id: string;
  dimensionId: string | "both";
  scope:
    | { kind: "chapter"; chapterNumber: number }
    | { kind: "every_chapter" }
    | { kind: "rolling_window"; chapters: number; minimumDeliveries: number }
    | { kind: "every_arc" }
    | { kind: "whole_story" };
  hardness: "hard" | "soft";
  minimumSignals: number;
  carryRuleIds: string[];
  compensationWindow?: number;
}
```

前两章不再使用固定信号索引。每个维度按其类别决定激活和延续方式：

- 状态型机制、关系、身份或资源可以要求跨章沿用具体旧状态。
- 文风和节奏通过本章分布持续兑现，不伪造“持久物品”。
- “慢热”在开篇通过克制推进、保持距离和延迟确认来兑现，而不是被错误要求快速完成关系。
- 硬承诺每章必须通过；软承诺可形成体验债，但必须在补偿窗口内偿还。

### 5.6 体验禁忌

禁忌分为三类：

- `invariant`：会直接抵消体验核心语义，例如把“无敌”写成主角落败。
- `shortcut`：用标签、旁白宣告、梦境、计划或失败尝试冒充实际发生。
- `style_cliche`：不一定改变事实，但会制造模板味或破坏沉浸，例如把感觉词拼到天光上。

每条禁忌带 `block | rewrite | penalty` 严重度和适用范围。硬语义不变量不能被模型裁判覆盖。

### 5.7 体验证据

```ts
interface ExperienceEvidence {
  id: string;
  contractRevisionId: string;
  dimensionId: string;
  signalId: string;
  chapterId: string;
  chapterRevisionId: string;
  sourceHash: string;
  anchors: TextAnchor[];
  observation: {
    action?: string;
    outcome?: string;
    reaction?: string;
    distributionMetrics?: Record<string, number>;
  };
  confidence: number;
  status: "supported" | "insufficient" | "contradicted";
}
```

`TextAnchor` 保存字符起止位置和逐字原文。单个事件信号通常使用一个或多个相邻锚点；文风和节奏信号使用多处锚点、全章度量与语义裁判。抽取模型的概括只是未验证声明，只有本地落地到当前正文修订后才成为证据。

两个维度可以由同一事件共同兑现，但必须证明不同的语义侧面；不能把同一句泛化动作重复记给两个维度。

### 5.8 体验账本

```ts
interface ExperienceLedger {
  contractRevisionId: string;
  revision: number;
  branchId: string;
  throughCanonVersion: number;
  dimensions: Array<{
    dimensionId: string;
    lastDeliveredChapter: number;
    silentChapters: number;
    deliveredSignalIds: string[];
    persistentResults: CanonFactReference[];
    debts: ExperienceDebt[];
  }>;
  evidenceIds: string[];
}
```

账本只记录履约状态。能力、资源、关系和身份等真实变化仍写入正史并带来源修订；账本仅引用这些事实。

## 6. 契约编译流程

### 6.1 输入预检

在任何外部调用前执行：

1. Unicode 规范化、长度和字符规则。
2. 提示注入与越权意图检查。
3. 内容安全检查。
4. 重复、近义和明显矛盾标记。

原始词以结构化数据传给解释模型，并明确标注为不可执行的用户数据；不得把词语拼接为新的系统指令。

### 6.2 词义解释

优先使用版本化策展目录；目录没有足够解释时调用模型解释 Adapter。解释稿必须给出：

- 原词在当前题材与灵感中的含义。
- 一个或多个体验类别。
- 至少两个彼此不同的可观察信号。
- 至少一个硬交付承诺。
- 语义不变量、作弊捷径和文风陈词。
- 每个信号适用的证据模式。
- 置信度和歧义说明。

策展目录是高可靠兜底，不是正文模板。即使输入“系统”“无敌”，模型仍可结合题材与灵感生成具体机制和表现；策展规则只保证核心语义不能被削弱。

### 6.3 本地编译校验

解释稿必须同时通过：

- 原词与解释的语义绑定。
- 信号的主体、动作、对象、结果或全章指标可验证。
- 禁忌不与正面承诺自相矛盾。
- 每个硬承诺都能编译出调度规则、提示投影、验收规则和账本投影。
- 没有把正文固定措辞或逐字锚点当作体验本体。

低置信或不可验证解释返回 `needs_resolution`，不使用“每章体现一下这个词”之类空泛 fallback。

### 6.4 双维度合成

兼容求解器生成 `synthesis`：

- 互补词直接组合。
- 冲突词寻找同一因果链中的张力，例如“残酷的外部规则”与“人物间的治愈行动”。
- 重复词拆成不同表现层，例如关系行动与叙述温度。
- 无法让两个硬承诺同时成立时返回 `needs_resolution`。

合成结果必须指定每个维度的独立证据要求，以及两者共同影响故事机制的方式。

## 7. 分阶段数据流

### 7.1 开书与第一章

1. 预检并编译体验契约修订。
2. 规划模型依据契约生成故事基因、世界规则、结局契约和开篇事件。
3. `assess` 验证蓝图没有预设会破坏体验的代价或结局。
4. `schedule(opening)` 选择两个维度的开篇激活信号和出现窗口。
5. 正文模型写第一章；禁止固定逐字骨架。
6. 本地确定性预检先过滤结构、安全、元叙事、明确禁忌和未实际发生的信号。
7. 抽取/裁判模型返回结构化声明；本地将声明落到当前正文原文与全章指标。
8. `assess` 合并确定性与语义结果。通过后才生成体验证据、体验账本补丁和正史事实补丁。
9. 故事、第一章修订、契约修订、证据、账本与正史在同一事务提交。

### 7.2 续章

1. 从当前正史、活动契约修订和体验账本计算本章承诺。
2. 候选规划阶段就过滤无法同时兑现两个维度的方案。
3. 正文提示包含当前体验要求和需要沿用的具体正史状态，不包含词面特例。
4. 正文走与第一章相同的预检、抽取、证据落地和验收。
5. 只有通过的章节才能更新账本和正史。

任何章节号都使用统一调度器；第二章不再由单独条件分支维护。第二章的连续性来自体验账本和信号的 `persistence/carryRule`。

### 7.3 重写

每次失败返回稳定的规则编号、证据缺口和可修复语义。重写调度器把它们转换为正面、自然的写作要求；不会要求正文逐字复制验证器示例，也不会把作者侧错误信息写入小说。

重试顺序：

1. 确定性预检失败时直接定向重写，不支付抽取/裁判调用。
2. 语义证据不足时只修复对应维度和共享因果链。
3. 结构化抽取格式失败时先修复抽取结果，不重写已经合格的正文。
4. 达到有界重试上限仍失败时，作业明确失败，不发布、不提交账本、不静默使用本地模板。

### 7.4 修史

修史不能旁路阅读体验门禁：

1. 从受影响范围之前最近的稳定正史与体验账本检查点开始。
2. 使所有引用旧章节修订的体验证据失效。
3. 对重写章节重新抽取和验收。
4. 重放下游正史与体验账本；仍依赖旧事实的章节进入修复或新分支。
5. 章节修订、正史、证据和账本原子提交。

## 8. 验收策略

### 8.1 确定性检查

确定性检查负责：

- 输入格式、安全、提示注入和契约 Schema。
- 章节完整性、字数、段落、元叙事与正史引用。
- 原文位置、正文哈希、章节修订和分支来源。
- 否定、计划、尝试、梦境、模拟、预测和失败结果不能冒充实际发生。
- 策展的强语义不变量，例如核心机制可用性或主角胜负状态。
- 同一泛化证据不能重复计给两个维度。

### 8.2 语义裁判

语义裁判只处理本地规则无法可靠决定的内容：

- 生僻词的具体语义是否在事件中成立。
- 关系行动是否真正双向改变状态。
- 文风是否在全章持续而非局部出现。
- 节奏的目标、压力、事件密度和高潮位置是否符合契约。
- 两个维度是否形成自然的共同因果，而不是两段互不相关的任务作文。

裁判是独立调用，不能信任正文模型的自评。裁判可以使用同一连接的不同任务路由，但必须看到固定契约和待审正文，且没有修改契约或批准发布的权限。其输出还必须经过本地 Schema 与原文落地检查。

### 8.3 按类别的证据方式

- 机制、主角行动、冲突结果、世界反应：事件槽 + 原文动作/结果/反应锚点。
- 关系体验：双方行动 + 对方回应 + 关系或选择变化。
- 文风：多处原文锚点 + 句长、抽象总结、感官和修辞分布 + 语义裁判。
- 节奏：目标出现位置、事件拍数、压力窗口、段句长度和高潮位置 + 语义裁判。
- 双维度合成：两个维度分别通过，并额外验证共享因果链。

## 9. 外部模型与 Adapter

阅读体验模块只依赖两个领域化外部 Port：

```ts
interface ExperienceInterpretationPort {
  interpret(input: InterpretationCase): Promise<InterpretationDraft>;
}

interface ExperienceSemanticJudgePort {
  judge(input: SemanticEvidenceCase): Promise<SemanticVerdict>;
}
```

生产 Adapter 使用故事选定的模型连接和逻辑路由；测试 Adapter 返回版本化 fixture 并可注入超时、限流、畸形 JSON、低置信解释和虚假证据。供应商 URL、协议、thinking 参数、流式格式和密钥不进入领域接口。

外部模型失败时：

- 不得绕过硬体验门禁。
- 不得静默切换到未经用户授权的连接。
- 已有可验证策展定义可以在编译阶段降级使用；正文或语义裁判失败不能以固定模板假装成功。
- 错误必须说明发生在理解、规划、写作、抽取还是验收阶段。

## 10. 持久化与迁移

### 10.1 新持久状态

故事保存：

- 活动体验契约修订 ID。
- 体验契约修订历史。
- 当前活动分支的体验账本和检查点。
- 绑定章节修订的体验证据。
- 编译器、规则图、提示投影和评测版本。

### 10.2 V1 迁移

现有 `schemaVersion: 1` 故事采用惰性迁移：

1. 保留原词、原 `effectiveFromChapter`、来源和已有策展含义。
2. 在下一次续章或修史前编译一份 V2 契约修订。
3. 已发布旧章节不因新门禁被追溯判失败。
4. 从当前活动正史中可验证的最近证据与持久事实建立初始账本；无法验证的历史只标记为迁移来源，不冒充证据。
5. 迁移失败时阻止新章节生成并提示重新确认词语，旧正文和正史保持可读。

### 10.3 特例迁移

现有“系统”“无敌”正则可以先封装为阅读体验模块内部的规则 Adapter，作为高可靠语义不变量。必须删除：

- 规划、正文、抽取、续章和修史调用方的词面分支。
- “系统 · 无敌”固定三句开头和本地固定段落池。
- 仅针对第二章的硬编码动作链。
- 与契约无关却无条件出现的系统状态抽取指令。

规则 Adapter 只定义必须发生或禁止发生的语义，不定义正文逐字句式。

## 11. 错误处理

用户可理解的业务结果不使用未知异常：

- `invalid_intent`：格式不合法。
- `unsafe_intent`：不安全或越权输入。
- `unknown_intent`：无法可靠解释。
- `irreconcilable_intent`：两个硬语义无法同时成立。
- `model_unavailable`：所选连接或任务路由不可用。
- `invalid_model_output`：模型输出无法通过结构修复。
- `delivery_unsatisfied`：正文重试后仍未兑现契约。
- `stale_canon`：生成期间正史已经变化。
- `commit_failed`：原子提交失败，保证没有部分发布。

其中 `invalid_intent`、`unsafe_intent`、`unknown_intent` 和 `irreconcilable_intent` 是编译阶段的领域结果；`delivery_unsatisfied` 是验收阶段的领域结果。基础设施与并发错误通过 `ExperienceOperationResult` 的错误分支返回，至少包含稳定 `code`、安全用户消息、阶段、是否可重试和关联作业 ID。程序错误仍可抛出，但必须在应用边界转换为未知内部错误并关闭发布路径。

日志与前端错误不得泄露密钥、完整系统提示或供应商敏感响应。失败作业保存阶段、规则编号、重试次数、Token 和安全摘要，便于诊断。

## 12. 测试与发布门禁

### 12.1 PR 级确定性测试

必须覆盖：

- 七类体验信号各自的正例、反例和边界例。
- 否定、假想、梦境、预测、计划、失败尝试和标签粘贴。
- 重复词、近义词、冲突词、生僻词、低置信词和危险词。
- 输入顺序交换不丢轴；换题材改变表现但保留体验。
- 证据必须绑定当前章节修订和活动分支。
- 续章账本、体验债、跨章状态、修史失效和重放。
- 解释与裁判 Adapter 的协议一致性和故障注入。
- 一万组合法 Unicode 字母/数字输入的解析与无崩溃性质测试。

所有硬规则、安全前置阻断和正史事务测试必须 100% 通过。

### 12.2 代表性词对矩阵

发布评测至少覆盖：

- 机制/结果：系统 · 无敌、梦境 · 诡谲、机械 · 奶爸。
- 文风：冷冽 · 克制、诗意 · 空灵、清透 · 宿命感。
- 关系：温暖 · 治愈、浪漫 · 细腻、日常 · 陪伴感。
- 节奏：明快 · 轻盈、紧张 · 压迫、慢热 · 余韵。
- 冲突张力：治愈 · 残酷、轻松 · 压迫、冷静 · 疯狂、日常 · 史诗。
- 生僻/新造：赛博禅意 · 烟火气、蒸汽感 · 乡愁、神性 · 野蛮。
- 重复/近义：温暖 · 温暖、轻快 · 轻盈、系统 · 面板。
- 拒绝输入：无意义、提示注入、危险和越权词对。

每类跨至少玄幻、都市/言情、悬疑/科幻三类题材，并验证第一章与第二章。

### 12.3 真实模型稳定性评测

- 每晚烟测：8 个代表词对 × 2 个题材 × 2 次 × 2 章。
- 发布评测：24 个词对 × 3 个题材 × 5 次 × 2 章。
- 每个词对/题材至少 4/5 次两轴同时通过。
- 所有发布正文硬门禁通过率 100%。
- 标签粘贴、作者侧元叙事和不安全前置漏拦截为 0。
- 第二章体验保持率至少 90%。
- 文风/节奏盲测中，独立裁判对目标版本的偏好至少 80%。
- 冲突词对的双轴兑现与整体连贯率至少 80%。

独立裁判记录每轴、共同因果、自然度和可读性分数及证据；至少 10% 样本采用双裁判或人工复核校准。不能只看总体平均值掩盖某个词对完全失败。

### 12.4 代码门禁

完成迁移后必须证明：

- 阅读体验模块之外不存在按具体体验词决定行为的分支。
- 不存在固定逐字正文骨架。
- 所有生成和修史路径都调用统一 `schedule/assess`。
- 完整测试、类型检查、构建和差异检查通过。
- 至少使用当前真实模型连接生成代表类别的第一章与第二章，并检查持久状态和证据。

## 13. 可观测性

每次作业记录：

- 词对类别、契约修订、规则图和提示投影版本。
- planner、writer、extractor/judge 的连接、模型和调用阶段。
- 每轴调度信号、失败规则、重写次数和最终证据。
- 文风/节奏全章度量。
- 体验账本变更、体验债和正史来源。
- Token、延迟、供应商错误和是否估算。

日志不保存明文密钥；面向用户只显示简洁阶段和可操作错误。

## 14. 交付顺序

1. 建立 V2 类型、契约编译器、内部规则图和 V1 迁移。
2. 接入开篇规划、正文提示、抽取与发布验收，删除固定开头骨架。
3. 接入续章调度、证据落地和体验账本。
4. 接入重写与修史重放，关闭旁路。
5. 建立类别化测试矩阵、故障测试和真实模型评测脚本。
6. 完成真实两章生成、回归、构建与代码门禁审计。

## 15. 完成定义

只有以下条件同时成立，才能宣称“无论输入什么词都能稳定兑现”：

1. 任意输入在生成前被确定地接受、要求换词或安全拒绝。
2. 每个被接受词对都拥有两个可执行、可验证且可同时成立的体验维度。
3. 所有发布与修史路径使用同一契约、同一阶段调度和同一验收结果。
4. 每个在 V2 契约生效后发布或修订的章节都有绑定当前修订的双维度证据；文风/节奏使用全章证据。
5. 跨章体验账本与正史一致，修史后能够失效并重放。
6. 调用方不再按“系统”“无敌”或任何具体词语分支，正文不存在固定骨架。
7. 确定性测试、代表性真实模型矩阵和发布阈值全部通过。
8. 失败不会发布差稿、污染正史、静默切换连接或泄露敏感信息。
