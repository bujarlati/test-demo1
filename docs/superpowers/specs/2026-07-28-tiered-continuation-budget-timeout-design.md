# 续写退修阶梯 Token 预算与超时设计

日期：2026-07-28
状态：产品设计已确认，等待书面规格审核
范围：续写章节在阅读体验审核不通过后的整章定向退修

## 1. 背景

续写作业目前对整个管线使用固定的 `50,000` Token 累计上限，Writer 的空闲超时固定为 5 分钟。首稿直接通过时，这组限制足以控制成本；但审核退回后，Writer 的下一稿还要携带完整上一稿、具体退修意见和锁定剧情，再支付一份完整输出及复审成本。继续沿用首稿上限会使退修在模型调用前被预算门拒绝，或在较慢的深度生成模型上更容易超时。

本设计让资源额度只在确实发生整章退修时按阶梯增加。首稿成功的作业保持现有成本和时限，不为可能永远不会发生的退修预留资源。

## 2. 已确认目标

1. 首稿直接通过时，累计 Token 上限仍为 `50,000`，Writer 空闲超时仍为 5 分钟。
2. 最多允许首稿加两次定向退修，共三稿。
3. 每多一稿，只提高作业累计 Token 上限和 Writer 超时。
4. 章节长度、目标字数和每稿 Writer 最大输出 Token 保持不变。
5. 一旦 Planner 产生有效计划，三稿都锁定该计划，正文退修不得重新规划；只有在尚未得到任何有效计划时，既有的 Planner 传输重试或显式连接回退才可再次请求规划。
6. 第二次退修基于上一版被退回稿件和最新审核原因修改，不退回最初首稿重写。
7. 只有结构化正文质量退修可以升档；网络、限流、JSON 修复和模型超时不升档。
8. 升档按需发生，并在下一次付费 Writer 调用之前校验 24 小时额度。
9. 第三稿仍不合格时终止，不开启第四稿，不降低审核或正史门禁。

## 3. 非目标

- 不提高开篇生成预算或超时。
- 不改变 Planner、Reviewer/Extractor 的超时。
- 不改变模型网关内部最多三次的瞬时网络或 JSON 重试规则。
- 不增加正文最大输出 Token，不放宽章节字数和段落数。
- 不提供用户可调的预算或超时设置。
- 不在前端暴露供应商级别的超时细节。
- 不通过切换模型、降低审核标准或发布未通过稿件来换取成功率。

## 4. 方案选择

采用固定宽裕阶梯。固定阶梯比运行时动态估算更容易预测、审计和测试，也避免保守的 UTF-8 字节预算估算在不同原稿长度下产生难以解释的上限。相比紧凑阶梯，它为“完整上一稿 + 退修信 + 完整修订稿 + 复审”保留了更可靠的空间。

| 逻辑稿次 | 含义 | 作业累计 Token 上限 | Writer 空闲超时 |
|---|---|---:|---:|
| 1 | 首稿 | 50,000 | 300,000 ms（5 分钟） |
| 2 | 第一次定向退修 | 110,000 | 480,000 ms（8 分钟） |
| 3 | 第二次定向退修 | 170,000 | 720,000 ms（12 分钟） |

`110,000` 和 `170,000` 是从作业开始计算的累计上限，不是每稿额外可使用的 Token 数。升档增量分别为 `60,000` 和 `60,000`。

## 5. 配置所有权

`server/generationBudget.ts` 是阶梯配置的唯一所有者，新增只读续写档位表和按逻辑稿次取档位的纯函数。建议的数据形状为：

```ts
interface ContinuationGenerationTier {
  attempt: 1 | 2 | 3;
  cumulativeTokenBudget: number;
  writerIdleTimeoutMs: number;
}
```

既有 `CONTINUATION_JOB_TOKEN_BUDGET` 保留为首稿预算的兼容别名，避免无关调用方一次性迁移；续写质量循环不得再把该别名当作所有稿次的硬上限。最大质量稿数由档位表长度推导，不再单独维护容易失配的数字常量。

配置必须满足以下启动时或单元测试不变量：

- 恰好三档，稿次连续且从 1 开始；
- 累计 Token 上限严格递增；
- Writer 空闲超时严格递增；
- 第一档与当前生产值完全相同；
- 所有档位使用相同的章节输出上限。

## 6. 续写数据流

### 6.1 首稿

1. 创建 `GenerationJob` 时只写入第一档 `tokenBudget = 50,000`。
2. 24 小时预算门只预留第一档。
3. Planner、候选审计、Writer 和 Reviewer 使用第一档累计上限。
4. Writer 使用 5 分钟空闲超时。
5. 首稿通过后直接提交，作业的 `tokenBudget` 保持 `50,000`。

### 6.2 第一次退修

1. Reviewer 或确定性正文校验抛出 `ChapterEditorialValidationError`，并带有可信的结构化退修问题。
2. 管线保存当前被退回稿件和问题，不重新运行 Planner。
3. 在启动第二次 Writer 前，把目标档位确定为第二档。
4. 当前作业已经预留 `50,000`，因此仅用 `60,000` 增量执行用户与小说的 24 小时预算校验。
5. 校验成功后，将 `job.tokenBudget` 更新为 `110,000` 并持久化；持久化完成后才允许启动 Writer。
6. Writer 使用完整上一稿、最新退修信和同一锁定剧情，空闲超时为 8 分钟。
7. 修订稿重新经过相同 Reviewer、阅读体验、内容安全、正史和硬约束门禁。

### 6.3 第二次退修

流程与第一次退修相同，但输入稿件是第二稿，审核问题是第二稿的最新问题。预算只再校验 `110,000 → 170,000` 的 `60,000` 增量，Writer 空闲超时为 12 分钟。第三稿通过后提交；仍失败则终止。

## 7. Token 预算语义

### 7.1 按需预留

升档函数接收当前作业、目标档位和现有作业列表。预算校验仍使用现有 24 小时用户上限 `1,500,000` 与单小说上限 `500,000`。因为运行中的当前作业已经按旧 `job.tokenBudget` 计入预留，校验请求值必须是：

```text
requestedBudget = targetTier.cumulativeTokenBudget - currentJob.tokenBudget
```

不得再次提交目标档位全额，否则当前作业会被重复计算。

### 7.2 持久化顺序

升档顺序固定为：

1. 计算并验证正增量；
2. 执行 24 小时预算校验；
3. 暂存旧 `job.tokenBudget`；
4. 写入目标档位并持久化；
5. 持久化成功后调用 Writer；
6. 持久化失败时恢复内存中的旧值并抛出错误。

这样其他请求读取运行中作业时能看到新的预留，且不会在预留尚未保存时先发生付费调用。

### 7.3 实际用量

- 所有成功和失败模型调用的可得用量继续累计到 `usedTokens`。
- 每次 Planner、Writer、Reviewer 调用前都使用当前档位减去 `usedTokens` 的余额执行既有保守准入检查。
- 完成或失败后，24 小时统计继续按作业实际 `tokens` 计费；未使用的运行期预留自然释放。
- 升档不改变 Writer 的 `maxOutputTokens`：紧凑、标准、长篇仍分别使用现有 `4,500`、`5,800`、`6,500` 上限。

## 8. 超时语义

`server/modelGateway.ts` 的续写 Writer 接口接收本稿 `writerIdleTimeoutMs`。默认值保持 5 分钟，以保证开篇和其他现有调用不变。

- 非流式 Writer：本稿总时限等于本稿空闲超时。
- 流式 Writer：继续使用现有长度倍数计算总时限。当前续写输出上限下，紧凑/标准稿使用 3 倍，长篇使用 5 倍。
- 因此三档紧凑/标准流式总时限分别为 15、24、36 分钟；长篇分别为 25、40、60 分钟。
- 网关内部网络重发共享当前逻辑调用的总截止时间，不重置截止时间，也不提升档位。
- Planner 保持 3 分钟；Reviewer/Extractor 保持 2 分钟。

“空闲超时”表示供应商在这段时间内没有产生可读取响应；流式模型持续返回内容时可以运行到总时限。两者都必须保持有界。

## 9. 重试、回退与终止规则

| 失败类型 | 是否升档 | 后续行为 |
|---|---|---|
| 结构化正文质量退修 | 是 | 保存本稿与问题，按需预留下档后定向退修 |
| 网络中断、连接超时 | 否 | 使用当前档位内的既有网关重试或显式路由回退 |
| 429/502/503/504 | 否 | 使用当前档位内的既有限次退避重试 |
| JSON 语法或 Schema 修复 | 否 | 使用当前档位和共享截止时间修复 |
| Reviewer/Extractor 不可用 | 否 | 按现有失败边界终止或进入既有审查流程 |
| 24 小时额度不足 | 否 | 下一稿 Writer 前返回明确的 429，不产生新调用 |
| 升档持久化失败 | 否 | 回滚内存档位并终止，不调用下一稿 Writer |
| 第三稿质量不合格 | 否 | 终止，不调用第四稿，不执行质量错误的路由回退 |

显式连接回退不得把当前档位重置为第一档，也不得因为重新发送请求而进入下一档。若有效计划已经产生，Writer 或 Reviewer/Extractor 的路由回退必须复用该计划；只有 Planner 自身在产生计划之前失败时，才允许既有回退重新请求规划，且这不计入正文稿次。质量稿次只由成功拿到完整稿件后发生的结构化审核退回推进。终端质量失败必须绕过模型路由回退，避免通过回退重新规划并生成第四稿。

## 10. 状态与并发

- `GenerationJob.tokenBudget` 是当前作业已预留的最高累计档位，也是恢复、预算统计和运维显示的事实来源。
- 逻辑质量稿次在一次续写请求内单调增加，不因网关重发或连接回退而重置。
- 同一小说既有写锁继续阻止两个续写事务同时修改正史。
- 重复请求仍由幂等键拦截；升档不会创建新作业或新幂等键。
- 不在数据库或长期状态中保存被退回正文；现有进程内退修上下文只存活到作业完成或失败。

## 11. 用户可见行为

前端不新增配置。流式阶段信息在退修时显示：

- 第一次退修：审核发现正文问题，正在基于上一稿进行第 1 次定向退修；
- 第二次退修：上一版仍有具体问题，正在基于上一稿进行第 2 次定向退修。

消息不展示 Token 数、内部错误堆栈或供应商细节。额度不足时返回明确提示，说明本次未启动下一稿，用户可在额度恢复后重新发起续写。

## 12. 审计、指标与隐私

每次成功升档记录结构化审计：

- 逻辑稿次；
- 原累计预算和目标累计预算；
- 本稿 Writer 空闲超时；
- 升档时已经消耗的 Token；
- 连接与作业标识。

不得记录正文、原文引用、审核理由、退修信内容或模型密钥。既有生成失败观测继续记录稳定原因码、稿次、是否终端、用量和延迟。运维侧可以据此计算首稿通过率、各档进入率、各档成功率、预算不足率和各档超时率。

## 13. 测试设计

### 13.1 纯函数与预算单元测试

- 三档值与严格递增不变量；
- 第一档保持 `50,000` 和 5 分钟；
- 档位越界被拒绝，不静默产生第四档；
- 运行中作业从 `50,000` 升至 `110,000` 时只校验 `60,000` 增量；
- 用户或小说额度不足时升档失败；
- 失败/完成作业按实际用量而非历史预留计入统计。

### 13.2 Writer 接口测试

- 三稿分别向 Writer 传入 300、480、720 秒；
- 三稿的 `maxOutputTokens` 按同一章节长度完全一致；
- 流式总时限分别由本稿空闲超时和现有长度倍数得到；
- 网关内部重试使用当前档位，不触发下一档。

### 13.3 续写管线测试

- 首稿通过：Planner 一次、Writer 一次、预算 `50,000`；
- 首稿退回、第二稿通过：Planner 一次、Writer 两次、预算 `110,000`；
- 前两稿退回、第三稿通过：Planner 一次、Writer 三次、预算 `170,000`；
- 第三稿提示词包含第二稿和最新问题，而不是首稿与过期问题；
- 第三稿失败后没有第四次 Writer，也没有质量错误触发的路由回退；
- 网络、限流、JSON、Writer 超时不会提升档位；
- 增量额度不足或持久化失败时下一稿 Writer 调用为零；
- 审计载荷不包含正文、引用或审核理由。

### 13.4 回归验证

- 编辑退修现有定向测试；
- 完整 `npm test`；
- `tsc --noEmit`；
- 生产构建；
- `git diff --check`。

## 14. 验收标准

1. 首稿成功作业的预算、超时、输出长度和调用次数与当前生产行为一致。
2. 只有结构化质量退修能依次进入第二、第三档。
3. 每次升档在 Writer 调用前完成增量额度校验与持久化。
4. 第二、第三稿分别获得 8、12 分钟 Writer 空闲超时和足够的累计预算。
5. 三稿共用同一剧情计划，后续稿只基于上一版与最新原因定向修改。
6. 第三稿失败后没有第四稿、质量路由回退或审核降级。
7. 日志与审计不泄露正文、审核理由或密钥。
8. 全部新增测试、完整回归、类型检查和生产构建通过。

## 15. 上线与观察

上线后重点观察：首稿通过率、进入第二/第三档比例、各档超时率、各档预算准入失败率、三稿最终成功率与实际 Token 分布。若第三档成本明显偏高但成功增益有限，后续只调整固定配置值，不改变本设计的按需预留、同一计划、最多三稿和质量错误专属升档语义。
