# “无敌”主旋律软性交付节奏设计

状态：已确认，待实施

日期：2026-07-29

范围：阅读体验契约、续章规划、正文验收、体验账本、失败观测与回归测试

关联：

## 1. 背景与问题

当前实现把“无敌”解释为逐章硬承诺：每一章都必须被确定性规则识别出“主角本人 + 决定性动作 + 对手 + 压倒性结果”。只要正文没有命中固定句式，即使章节作为小说是合格的，也会被 `missing_required_outcome` 拒绝并连续重写。

2026-07-28 的线上第三章续写连续三次因此失败。该故事的主旋律确实是“无敌”，但第三章并不需要再次重复压倒性胜利；把主旋律等同于逐章考试既破坏节奏，也制造了高误杀率。

本设计把两类要求拆开：

1. 主角不能出现已经落地的最终失败，这是每章硬性底线。
2. 压倒性胜利是跨章主旋律，目标为三章内至少交付一次，但不作为单章发布门禁。

## 2. 产品规则

### 2.1 每章硬性底线

以下已经发生且结论明确的结果继续阻止发布：

- 主角投降、认输或向敌方臣服；
- 主角被彻底击败、失去继续行动能力，并由他人救场才保住结果；
- 主角的核心能力或系统被永久封印、撤回或转交，导致既定主旋律失效；
- 最终胜利实际上由同伴、护卫或其他第三方完成，主角只是旁观或被救。

审核必须绑定主角、真实对手、已发生动作和已落地结果。假想、预言、敌人的计划、被否定的说法以及系统模拟不得被当作真实落败。证据不明确时按软性问题处理，不得硬拒绝。

### 2.2 允许的战斗过程

以下内容不再触发硬门禁：

- 双方暂时五五开或势均力敌；
- 主角受伤、被压制或短时间处于劣势；
- 一章结束时战斗尚未分出胜负；
- 主角主动停手、撤离或等待系统任务完成，但正文没有把它写成最终落败；
- 纯铺垫、关系、探索、经营或世界反应章节没有安排正面对抗。

五五开可以跨一章。下一章规划必须优先继承该冲突，并安排“完成系统任务或条件 → 实力/权限产生变化 → 主角压倒性取胜”的收束方向；若写作模型仍未兑现，则继续记录体验债，不让本次续写失败。

### 2.3 压倒性胜利的软性节奏

- 目标窗口：任意连续三章中至少有一次压倒性胜利。
- 新故事从体验契约生效章开始计算；第一章不再要求命中固定胜利句式。
- 旧故事不追溯历史体验债，从升级后的下一次成功续写开始计算。
- 一旦安排胜利，质量目标仍是主角亲自完成、对手明确失去反抗能力，并产生可观察结果；险胜或含糊收场不计为压倒性胜利。
- 未在目标窗口兑现时，章节仍可发布，同时打开体验债并强化下一章规划。

“三章”是规划目标，不是新的第三章硬门禁。

## 3. 方案选择

### 3.1 采用：软性主旋律账本

确定性验收只保留高精度的最终落败底线；正向的压倒性胜利由语义审稿器识别并写入跨章账本。缺少正向证据只产生体验债，不抛出章节质量异常。

### 3.2 未采用：三章截止硬门禁

这种方案前两章放行、第三章强制重写，虽然比逐章门禁宽松，但仍可能因为表达方式不被识别而让用户反复生成失败。

### 3.3 未采用：继续扩充胜利正则

扩充动词、对手和结果词表只能移动误判边界，无法覆盖开放的小说表达空间，也与通用体验词架构相违背。

## 4. 契约与数据模型

### 4.1 按体验轴声明交付策略

在现有 `ReadingExperienceContract.delivery` 下增加可选的按轴策略，保持 `schemaVersion: 1`，让旧代码回滚时忽略新增字段：

```ts
interface ReadingExperienceAxisDeliveryPolicy {
  axisId: "primary" | "secondary";
  mode: "hard_every_chapter" | "soft_window";
  targetWindowChapters: number;
  targetMaxOpenConflictChapters: number;
}
```

“无敌”的策展定义声明：

```ts
{
  mode: "soft_window",
  targetWindowChapters: 3,
  targetMaxOpenConflictChapters: 1
}
```

运行路径不得用 `sourceWords.includes("无敌")` 决定规则；续章规划和验收只读取契约中的策略。词语到策略的映射只存在于契约编译数据中，符合“词义是数据而不是代码”的架构原则。

契约编译与旧契约规范化还必须同步处理现有冲突字段：

- 把“无敌”的逐章硬承诺从“全程不败、不五五开”改为“不能形成主角已经落地的最终失败”；
- “长期五五开会稀释主旋律”保留为软性节奏风险，单章或跨一章五五开不再属于禁止捷径；
- `soft_window` 轴在 `openingRequirements` 中的正向信号改为规划建议，不进入逐章必需信号硬校验；
- Writer 与审稿提示必须把该轴标为“主旋律节奏目标”，不得继续显示为“本章硬契约”。

这样可避免一边放宽发布门禁，一边仍由旧提示强迫 Writer 每章写胜利的内部矛盾。

### 4.2 体验交付账本

故事记录增加可选的按轴账本：

```ts
interface ReadingExperienceDeliveryLedgerEntry {
  axisId: "primary" | "secondary";
  lastEvaluatedChapter: number;
  lastDeliveredChapter?: number;
  silentChapters: number;
  debtOpen: boolean;
  openConflictSinceChapter?: number;
}
```

账本只在章节成功发布后更新，不记录失败草稿：

- 识别到压倒性胜利：`silentChapters = 0`，关闭体验债和未决冲突；
- 没有识别到胜利：`silentChapters += 1`；
- 出现五五开或未决冲突：记录 `openConflictSinceChapter`；
- `silentChapters >= 3`：打开体验债，但不阻止发布。

旧故事没有账本时，以升级后的最新已发布章节作为基线，设置 `silentChapters = 0`，不扫描历史正文追债。

### 4.3 语义审稿结果

审稿结果为节奏账本提供结构化状态：

```ts
type InvincibleConflictState =
  | "no_conflict"
  | "open_parity"
  | "dominant_victory"
  | "conclusive_defeat";
```

`dominant_victory` 用于偿还体验债；`no_conflict` 与 `open_parity` 可以发布；只有证据明确的 `conclusive_defeat` 进入定向退修。

## 5. 续章数据流

### 5.1 规划前

1. 加载阅读体验契约与交付账本。
2. 根据 `silentChapters`、`debtOpen` 和 `openConflictSinceChapter` 计算本章节奏：
   - `0–1`：正常创作，可安排铺垫或其他剧情；
   - `2`：把压倒性胜利提升为本章高优先级方向；
   - 已有未决五五开：要求优先继承并收束该冲突；
   - `>= 3`：标记体验债，继续强化胜利方向，但不转成发布门禁。
3. 把节奏要求写入候选规划和 Writer 提示，不提供固定句式。

### 5.2 写作与审稿

1. Writer 按本章计划生成正文。
2. 审稿器结合整段上下文判断冲突状态，并引用最接近的正文证据。
3. 确定性层只检查安全、结构、最低字数及高精度最终落败底线。
4. 正文没有压倒性胜利时，不再抛出 `missing_required_outcome`。
5. 明确最终落败时，生成带 `sourceQuote`、原因和修改要求的退修问题，把原稿交回 Writer 定向修改，不另起炉灶。

### 5.3 发布后

1. 保存章节修订和语义审稿结果。
2. 更新体验交付账本。
3. 记录脱敏节奏事件，供后台观察和后续规划使用。

## 6. 错误处理与观测

### 6.1 不再视为生成失败

以下情况不得触发重试或终止作业：

- 本章没有压倒性胜利；
- 审稿器无法找到可靠胜利证据；
- 三章窗口到期但 Writer 仍未兑现；
- 一章以五五开或未分胜负结束。

这些情况分别记录为 `experience_cadence_silent`、`experience_debt_opened` 或 `open_conflict_carried`，属于规划观测而非失败观测。

### 6.2 仍属于退修问题

明确最终落败使用稳定原因码 `explicit_protagonist_defeat`。退修问题必须包含：

- 最接近问题的短原句，仅用于当前作业的定向修改；
- 为什么这是已经落地的最终失败，而不是暂时五五开；
- 在保留人物、对手和已有剧情的前提下如何改成未决冲突或主角最终取胜。

跨作业失败观测继续遵守隐私 ADR：不保存完整正文或原始提示词。后台长期记录只保留原因码、章节、模型、尝试次数与账本状态。

### 6.3 降级原则

审稿证据含糊、缺少主角绑定或无法判断结果是否最终落地时，一律降级为软性提醒，不允许硬拒绝。宁可产生一章体验债，也不因不确定判断让用户连续生成失败。

## 7. 兼容与迁移

- PostgreSQL 表结构不变；新增策略和账本均位于现有故事 JSON 载荷中。
- 新建故事由契约编译器直接写入按轴策略。
- 旧故事在读取时由通用契约规范化器从策展定义补齐策略，并在下一次正常故事写入时持久化。
- 规范化器同时替换旧的逐章“不五五开”承诺，并把软窗口轴从开篇逐章必需信号中移出。
- 规范化器通过策展定义数据查表，不在运行路径增加“无敌”词面分支。
- 旧故事第一次采用新策略时从零债务开始，不追溯已有章节。
- 回滚旧版本时，旧代码继续读取 `schemaVersion: 1` 并忽略新增字段。

## 8. 测试设计

### 8.1 单章验收

应放行：

- 纯铺垫章没有正面对抗；
- 主角与对手暂时五五开；
- 主角短暂受伤或受压，但没有最终落败；
- 章末战斗尚未分出胜负；
- 主角先五五开，完成系统任务后在同章压倒性获胜；
- 胜利使用自然表达、没有命中旧正则词表。

应定向退修：

- 主角明确投降或认输；
- 主角被彻底击败后由第三方救走；
- 主角永久失去核心能力并导致既定体验失效；
- 第三方代打完成最终胜利，主角没有实际参与结果。

### 8.2 跨章节奏

- 连续两章没有胜利时，第三章计划包含高优先级胜利方向；
- 五五开章发布后，下一章计划继承同一冲突并安排收束；
- 第三章仍未胜利时可发布，同时打开体验债；
- 后续出现压倒性胜利后，账本清零并关闭体验债；
- 旧故事首次加载时不产生历史债务；
- 幂等重试不得重复增加 `silentChapters`。

### 8.3 回归与线上验证

- 原先因缺少“无敌”胜利句而三次失败的固定案例应一次通过单章质量门禁；
- 现有明确落败、救场和永久削弱案例仍应失败；
- 全量单元测试与构建通过；
- 生产发布后验证服务、Nginx、公网健康、PostgreSQL 持久化和启动日志；
- 观察新原因码，确认不再出现仅因缺少压倒性胜利导致的终止作业。

## 9. 实施边界

本次包含：

- 按轴软性交付策略与账本；
- 续章规划节奏注入；
- 删除“无敌”每章正向硬门禁和“五五开”词面硬拒绝；
- 明确落败的定向退修；
- 脱敏节奏观测与回归测试。

本次不包含：

- 面向读者展示体验债的新界面；
- 修改已发布章节或追溯重算旧故事；
- 对所有体验词一次性完成通用语义裁判重构；
- 改变模型连接、Token 阶梯或超时配置。

## 10. 验收标准

1. 合格铺垫章、五五开章和未决冲突章不因缺少压倒性胜利而失败。
2. “无敌”压倒性胜利按三章目标进入规划，未兑现只产生体验债。
3. 主角明确最终落败仍被阻止，并使用原稿定向退修。
4. 运行路径不新增按“无敌”字符串分支，策略来自契约数据。
5. 旧故事无需重建、无需 SQL 迁移且不产生历史债务。
6. 不再出现仅因 `missing_required_outcome` 的压倒性胜利缺失而连续三次重写并终止作业。
7. 新增观测不保存完整正文，符合失败观测隐私 ADR。
