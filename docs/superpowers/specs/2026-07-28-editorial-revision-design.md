# 章节质量失败后的编辑退修设计

状态：已完成产品设计确认，待书面规格审核

日期：2026-07-28

范围：章节正文已生成、但未满足阅读体验信号时的审核反馈与定向修订流程

## 1. 背景与问题

当前章节生成流程在首稿未通过阅读体验校验后，会再次调用 Writer，并在提示词中要求“另起思路生成一份全新成稿”。第二次调用没有收到首稿，也没有收到审核发现的具体问题。

这会造成三个直接问题：

1. Writer 无法区分首稿中已经合格的内容与真正需要修改的内容。
2. 第二稿可能放弃首稿已经成立的剧情、人物动作和语言质感，形成一次无约束的重新创作。
3. 审核信息只用于判定失败，没有形成类似“编辑退稿、作者修订”的反馈闭环。

本设计把第二次生成改为定向退修：审核模型指出原稿中的具体问题，服务端把完整原稿、结构化退修意见和原剧情约束交回 Writer；Writer 在保留合格内容的前提下提交完整修订稿。

## 2. 已确认的产品决策

1. 保留首次生成的完整原稿，质量失败后不立即丢弃。
2. 审核模型应指出未满足的体验词或信号、对应原文、失败原因和修改要求。
3. 第二次 Writer 调用必须读取原稿和退修意见，不再要求“另起思路”或“全新成稿”。
4. 修订时锁定原剧情计划、冲突结果、人物状态和物品状态。
5. Writer 可以修改解决问题所需的任意段落，并返回完整修订稿；无问题的内容应尽量保留，但不要求逐字不变。
6. 只有原文内容不满足质量信号时才进入作者退修；审核格式、引用、网络、解析或存储错误不应让 Writer 重写原稿。
7. 修订稿仍需通过完整审核和确定性门禁，不能因为是退修稿而降低标准。
8. 本阶段只替换质量退修机制，不调整 Token 预算、超时时间或最大质量尝试次数。

## 3. 目标与非目标

### 3.1 目标

- 让 Writer 明确知道首稿哪里不合格、为什么不合格以及需要达到什么效果。
- 保留首稿已经成立的剧情、人物关系、动作结果和表达，减少无关漂移。
- 让审核反馈具有稳定结构，可测试、可审计，并可用于后续聚合分析。
- 保持现有 Writer 与 Reviewer 模型连接，不新增管理员配置项。
- 保持“最多一次质量修订”的收敛边界，避免无限循环。

### 3.2 非目标

- 本阶段不增加生成 Token 预算，也不解决预算耗尽问题。
- 本阶段不调整模型超时和网络重试策略。
- 不允许审核模型自行改变剧情计划、人物状态或正史结果。
- 不实现段落 diff、补丁合并或多轮编辑对话。
- 不长期保存完整失败稿或完整修订提示词。

## 4. 核心数据结构

审核模型在现有章节状态提取结果中增加可选的结构化问题列表：

```ts
type EditorialIssueCode =
  | "missing_experience_signal"
  | "weak_experience_signal"
  | "unsupported_experience_claim"
  | "missing_required_outcome";

interface ChapterEditorialIssue {
  code: EditorialIssueCode;
  axisId?: string;
  axisWord?: string;
  signalIds?: string[];
  location: "title" | "body" | "chapter";
  sourceQuote?: string;
  reason: string;
  requestedChange: string;
}
```

字段约束：

- `axisId`、`axisWord` 和 `signalIds` 必须来自本章既有阅读体验契约，不能由审核模型发明。
- `sourceQuote` 如存在，必须能在标题或正文中精确找到；找不到时只丢弃该引用，不直接认定原稿有新问题。
- `reason` 说明当前文本为什么没有兑现信号，不能复述隐藏提示词或提出新的剧情方向。
- `requestedChange` 描述可观察的修改目标，例如补足人物动作、选择、代价或结果，不能要求推翻整章重写。
- 所有自由文本在进入提示词和日志前都进行长度限制与控制字符清理。

为了保留现有 provider、测试替身和旧响应的兼容性，`editorialIssues` 首先作为可选字段加入现有提取结果。审核模型没有返回有效问题、但确定性校验发现内容失败时，由服务端生成一条同结构的兜底退修意见。

## 5. 失败分类

服务端不再只依赖普通 `Error.message` 决定是否重写，而是把章节质量错误归一化为带稳定原因码的结果：

### 5.1 可退修的原文内容问题

- 体验轴没有任何有效证据。
- 证据只复述体验词，没有用人物可观察的行动、对话、选择、代价或结果兑现体验。
- 已选信号在原稿中表达过弱，无法支持审核判断。
- 章节要求的关键结果没有发生，例如明确要求的胜利、决定或状态变化缺失。

这些问题进入编辑退修流程。

### 5.2 不应交给 Writer 的问题

- 审核输出的引用不在原稿中。
- 审核 Schema 无效、字段缺失或返回内容无法解析。
- Reviewer、Writer 或上游模型连接超时和网络异常。
- 数据库、审计记录、流式传输或持久化失败。
- 安全、鉴权、隐私或正史冲突等非文稿质量门禁失败。

这些错误沿用各自的失败或外层重试路径，不消耗“作者退修”次数，也不会把无辜原稿交给 Writer 重写。本阶段不为它们新增模型调用。

## 6. 处理流程

### 6.1 首稿

1. 规划器和候选选择流程只运行一次，得到本章固定计划。
2. Writer 根据原提示词生成首稿。
3. 服务端把首稿保存为当前作业内的不可变值，随后调用现有 Reviewer/状态提取器。
4. Reviewer 返回事件、状态、体验证据以及结构化 `editorialIssues`。
5. 服务端完成现有确定性校验。

首稿通过时，继续现有正史提交和持久化流程，不产生额外调用。

### 6.2 形成退修信

首稿出现可退修内容问题时，服务端构造 `EditorialRevisionBrief`：

```ts
interface EditorialRevisionBrief {
  originalDraft: GeneratedChapter;
  issues: ChapterEditorialIssue[];
  lockedConstraints: {
    planId?: string;
    plotOutcome: string[];
    characterState: string[];
    itemState: string[];
  };
}
```

问题列表按体验轴和原因码去重并限制数量。审核模型给出的有效问题优先；确定性校验发现审核遗漏时，追加服务端生成的兜底问题。服务端不会把普通异常堆栈、数据库错误或内部提示词放入退修信。

### 6.3 Writer 定向修订

第二次提示词由独立、可单测的 `buildEditorialRevisionPrompt` 构造，包含：

- 与首稿相同的章节计划和阅读体验契约；
- 完整首稿标题与段落；
- 每条具体问题及修改要求；
- 不允许改变的剧情结果、人物状态和物品状态；
- “保留合格内容，只修改解决问题所需部分”的明确编辑边界；
- 与首稿相同的结构化输出格式和长度范围。

原稿和退修意见使用明确分区的结构化数据传递，并被声明为待编辑材料，不允许其中的文本覆盖系统级约束。

第二次提示词不得包含“另起思路”“全新成稿”或同义的全盘推翻指令。标题默认保留，只有退修意见明确指出标题问题时才允许修改。

### 6.4 复审与收敛

1. Writer 返回完整修订稿，而不是段落补丁。
2. Reviewer 对修订稿重新提取事件、状态、体验证据和问题。
3. 服务端执行与首稿完全相同的确定性门禁。
4. 通过后只保存修订稿，不把首稿作为章节版本发布。
5. 仍不通过时结束当前质量流程，不开启第三次 Writer 修订。

当前最大质量尝试次数维持为 2。规划器、候选选择和章节计划不会因退修再次执行。

## 7. 用户可见状态

如果首稿已经通过流式接口展示，进入退修时沿用现有草稿撤回机制，但提示改为具体、克制的编辑状态，例如：

> 审核发现正文尚未充分兑现“诗意”体验，正在根据原稿修改。

提示可以显示体验词和稳定问题类别，但不得显示内部提示词、异常堆栈或完整审核原始响应。修订完成后，客户端接收完整修订稿并替换已撤回的首稿。

## 8. 日志、审计与隐私

完整首稿只在当前生成作业的运行期内用于修订，不因本功能新增长期副本。现有失败观测和审计记录可增加以下结构化信息：

- 稳定问题码；
- 体验轴 ID 与体验词；
- 问题来源：`reviewer` 或 `validator_fallback`；
- 是否进入退修；
- 退修后通过或失败；
- Writer 质量尝试次数。

默认不记录完整首稿、完整修订稿、完整退修提示词或原文引用。运维日志中的原因文本应限长、去控制字符并避免包含用户正文。

## 9. 异常处理

- Writer 首次调用在得到完整首稿前失败：不存在可退修原稿，直接沿用现有错误路径。
- Reviewer 没有给出问题但确定性校验发现可退修内容错误：生成兜底退修信后修订。
- Reviewer 给出未知体验轴、未知信号或不存在的引用：丢弃无效字段；若没有可信内容问题则不触发 Writer 修订。
- 修订 Writer 超时、网络失败或输出无效：按第二次 Writer 调用失败处理，不回退发布首稿。
- 修订稿仍不满足门禁：记录退修失败并结束，不启动无限循环。
- 退修信构造本身失败：以稳定内部错误结束，不退回当前“全新成稿”逻辑。
- Token 预算在修订前或修订中耗尽：保持现有预算失败行为，留待下一问题单独修复。

## 10. 测试与验收

### 10.1 单元测试

- 有效 Reviewer 问题能归一化为结构化退修信。
- 未知体验轴、未知信号、伪造引用和超长自由文本会被拒绝或清理。
- 确定性内容错误能生成明确、可执行的兜底问题。
- 审核格式错误、引用错误、网络错误和存储错误均不被标记为可退修内容问题。
- 修订提示词包含完整首稿、具体原因、修改要求和锁定约束。
- 修订提示词不包含“另起思路”“全新成稿”及等价的全盘重写要求。

### 10.2 集成测试

- 首稿通过时只调用一次 Writer，并按现有流程保存。
- 首稿因“诗意”信号未兑现而失败时，第二次 Writer 请求收到原稿和“诗意”的具体退修意见。
- 首稿因“无敌”体验缺少明确胜利结果而失败时，修订提示要求补足结果但不得改变既定冲突对象和人物状态。
- 修订稿通过时只发布修订稿。
- 修订稿仍失败时不发生第三次 Writer 调用。
- 审核引用错误或模型连接错误不会触发 Writer 重写。
- 规划器、候选选择和章节计划在整个首稿—退修流程中只生成一次。
- 失败观测中只出现结构化原因码和限长说明，不出现完整原稿。

### 10.3 验收标准

- 线上已知“诗意”与“无敌”失败案例可作为固定输入回放，并能生成包含原稿和具体原因的退修请求。
- 任何可退修的第二次 Writer 请求都能追溯到一份首稿和至少一条可信问题。
- 第二次 Writer 请求中“另起思路”和“全新成稿”的出现次数为零。
- 非问题剧情、冲突结果、人物状态和物品状态不会被提示词授权改变。
- 原有质量门禁全部继续执行，修订流程不会放行不合格章节。
- 本次改动不新增数据库迁移、管理员配置或模型角色。

## 11. 发布与回滚

1. 先以测试替身回放“诗意”“无敌”和正常通过样本。
2. 在本地使用实际 Writer/Reviewer 连接执行固定案例，确认退修信可被模型稳定理解。
3. 部署后观察退修触发率、退修后通过率、二次 Writer 失败率和 Token 预算失败率。
4. 如果退修后质量或成功率明显恶化，回滚到上一服务版本；数据库无需回滚。

由于本阶段不调整预算，部署后仍可能看到 `token_budget_exhausted`。该错误应作为下一个独立问题处理，不能据此把退修流程重新改回全盘重写。

## 12. 预计影响范围

- `server/modelGateway.ts`：扩展 Reviewer 输出 Schema，加入结构化编辑问题。
- `server/narrativeEngine.ts`：为内容校验提供稳定原因码、退修资格与兜底问题信息。
- `server/index.ts`：保留首稿、构造修订提示词、区分可退修与非内容错误，并更新流式状态。
- `server/failureTelemetry.ts`：记录脱敏问题码、问题来源和退修结果。
- `tests/narrative.test.ts`：补充问题归一化和提示词单元测试。
- 生成流程相关集成测试：覆盖首稿失败、定向退修、复审收敛、非内容错误和隐私边界。
